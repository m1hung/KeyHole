# Security policy

Keyhole is a password manager, so a report about it is worth more than a report
about most software. This document says how to send one, what is in scope, and
what is already known — so that finding something real is not competing for
attention with the same four non-issues.

## Reporting a vulnerability

**Use GitHub's private vulnerability reporting**: the
[Security tab](https://github.com/m1hung/KeyHole/security/advisories/new) →
*Report a vulnerability*. That opens a private thread visible only to the
maintainer, and it can become a published advisory once there is a fix.

**Please do not open a public issue for anything that lets an attacker reach a
vault, a master password, or a key.** A public issue on a password manager is a
working exploit handed to everyone still running the old build — and since
Keyhole has no auto-update channel, "everyone" stays large for a long time.

Useful things to include: the surface (desktop app, extension, sync server, iOS),
the commit or build you tested, and what an attacker gets. A proof of concept is
welcome but not required — a clear description of the flaw beats none at all.

### What to expect

This is a **single-maintainer project with no bug bounty**. There is no paid
triage rota and no service-level promise that would survive contact with a busy
week. In practice: a first response is the realistic goal within about a week,
and reports that clearly reach vault data are the ones that get dropped
everything for. If you have had no reply in two weeks, assume the message was
missed and ping the thread.

Credit in the advisory and the commit is offered by default; say so if you would
rather stay anonymous.

## Supported versions

| Version | Supported |
|---|---|
| `main` | ✅ Fixes land here |
| Any built `.exe` or unpacked extension you are holding | ⚠️ Only if it matches `main` |

There are **no tagged releases yet**, which means there is no such thing as a
patched version you can upgrade to — the fix is a rebuild from source. If you are
running the portable `.exe`, you are running whatever the tree looked like on the
day it was built. Rebuild with `npm run build:desktop` and replace the binary
yourself; there is deliberately no update channel, because an auto-updater is a
remote-code path into a password manager.

## In scope

Anything that breaks a claim the [threat model](README.md#threat-model) makes:

- **Crypto and the vault format** — key derivation, the AES-GCM layers, the associated-data binding, the KDF-downgrade floor, anything that lets a stolen vault file be read or silently altered.
- **Extension messaging** — a web page, a content script, or another extension reaching a privileged handler; anything that gets a credential out of the service worker without the explicit per-credential click.
- **Autofill targeting** — a credential delivered to the wrong origin or the wrong frame, a lookalike or shared-hosting host that matches when it should not.
- **Storage and lock state** — key material persisted anywhere, a stale "unlocked" state, secrets surviving a lock.
- **The sync server** — one account reading or overwriting another's envelope, auth bypass, anything that makes the server able to read what it stores.
- **The desktop shell** — escaping `contextIsolation`/`sandbox`, plaintext crossing the preload bridge, the renderer reaching Node.

## Out of scope

These are documented properties, not oversights. Reports about them will be
closed with a pointer here.

- **Everything under [Not defended](README.md#not-defended--be-honest-about-this)** — keyloggers, a compromised OS, malware with process-memory access, another extension with `<all_urls>`, evil-maid with a memory dump, a backdoored browser. Nothing in a browser or an Electron app defends against these, and pretending otherwise would be the actual security problem.
- **`examples/demo-vault.keyhole.json` and its published master password.** Deliberate. The file exists to be opened; it holds five fabricated entries on RFC 2606 reserved domains. Finding that it decrypts is the intended behaviour.
- **The 16 `npm audit` advisories.** All dev-only, all one `brace-expansion` DoS reached through `electron-builder`. `npm audit --omit=dev` reports zero, the packaged `app.asar` contains no `node_modules` at all, and the reasoning is written out in [About `npm audit`](README.md#about-npm-audit). CI enforces the production number stays zero.
- **The unsigned build / SmartScreen warning.** Known. Code signing costs money and is listed as out of scope for v1.
- **No recovery from a forgotten master password.** That is the design.
- **Missing security headers on the sync server's status page**, unless you can turn it into something that reaches an envelope or the control listener.
- **Reports generated by a scanner with no analysis attached.** "This is a password manager, so it is high risk" is not a finding.

## If you are checking Keyhole yourself

[`docs/SECURITY-CHECKLIST.md`](docs/SECURITY-CHECKLIST.md) is the manual pass the
maintainer runs after touching crypto, storage or messaging. It is a reasonable
place to start, and if it is missing a check that would have caught something
real, that itself is worth reporting.
